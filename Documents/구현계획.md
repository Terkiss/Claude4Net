## 0. Product Direction

Claude4Net-App has completed the K023-K028 expansion from a Windows-stable CLI into a file-backed, observable, multi-agent runtime. The next phase should consolidate the runtime into an operational agent platform rather than continue adding isolated features.

The product identity is:

> Claude4Net-App is a trusted execution environment where .NET developers can safely, transparently, resumably, and verifiably delegate real development work to AI agents.

The next roadmap is based on the 2026-05-10 insight report and follows four product pillars:

1. State Discipline: explicit session state machines, checkpoints, rewind, resumability
2. Safe Execution: idempotent file operations, diff-first approval, verifier gates, fail-closed policies
3. Provider Architecture: descriptor-first providers, capability-aware routing, observable health
4. Operational Visibility: replayable events, timeline-based diagnostics, auditable results, controller-grade dashboards

The following detailed themes from the insight set must remain visible in planning:

- real token counting instead of heuristic-only estimates
- handoff and evidence artifacts as completion preconditions
- fresh-context evaluator separation with default-fail verification contracts
- CQRS-style event projections for dashboard scalability
- agentic search as the first recall path, with RAG as an explicit secondary tool
- audit-log fields designed for enterprise and regulatory traceability

CLI-first execution remains the primary product rule. Dashboard work is allowed only when it directly improves operations, visibility, or approvals.

## 3. Operating Roles

### Gemini CLI Worker

- Implements assigned work
- Modifies code, tests, and docs
- Runs the official release gate
- Does not commit or push

### Gemini 3.1 Pro First Reviewer

- Reviews worker output
- Checks staged and unstaged diffs
- Re-runs the release gate when needed
- Writes P1/P2/P3 findings
- If work is not ready, writes the correction prompt
- Does not escalate to Codex until blocking findings are cleared
- Does not commit or push

### Codex Final Controller

- Reads the actual repository state before trusting reports
- Makes final approval, commit, and push decisions
- May directly perform small, scoped, evidence-backed documentation or hygiene corrections
- Keeps branch policy and release gates aligned

Future priorities after K037 are derived from `Documents/Project_Lumen_CLI_UI_Design_Plan.md`. The Lumen queue must be executed in small, reversible milestones. Do not attempt a full CLI rewrite in one worker run.

Cross-milestone dependency rules:

- K029 must precede any broad autonomous-write work because rollback and handoff evidence are the safety baseline.
- K030 should land before K034 because projections are much more useful when the write-side lifecycle states are explicit.
- K032 should land before high-risk automation because verifier separation and default-fail evidence rules are the quality baseline.
- K031 can run after K029/K030 or in a short isolated branch, but it must not change provider transport behavior without descriptor tests.
- K033 should wait until K032 exists so automatically generated skill proposals can be verified independently.
- K035 can be split if needed: retrieval strategy may ship separately from enterprise audit fields.

Global acceptance rules for future milestones:

- Every milestone must add at least one regression test for the highest-risk failure mode.
- Any new file-backed state must be stored below `.claude4net/` unless explicitly documented otherwise.
- Any user-visible PASS, Completed, Approved, or Ready status must be backed by a command output, evidence file, or machine-readable result.
- Any feature that can mutate files must have path traversal protection and a no-op/idempotency story.
- Dashboard changes must remain read-oriented unless a separate approval/control contract is defined.

Project Lumen acceptance rules:

- Preserve the current CLI behavior until the new Lumen path is verified.
- Add or reserve `--legacy-cli` before replacing interactive behavior.
- Do not modify Discord, dashboard, or piped-input behavior unless the milestone explicitly allows it.
- Do not replace approval flow, prompt composer, renderer, and AgentLoop output in the same milestone.
- Keep `AgentLoop` usable without any Lumen dependency.
- UI-facing runtime observation must use neutral SDK/runtime contracts, not Spectre.Console types.
- Project Lumen v1 must not add a new terminal framework package. Use the existing Spectre.Console dependency unless the final controller explicitly approves a package change.
- The Lumen UI loop must remain alive while an agent run is active. Long-running agent execution should be represented as a background run task so approval prompts, cancellation, and render updates cannot deadlock the input loop.
- Rendering updates must be serialized through a dispatcher, reducer, lock, or equivalent single-writer mechanism so background output and key input do not corrupt each other.
- Every Lumen milestone must include focused tests and the official release gate.
- Any document under `Documents/` that should be committed must be staged explicitly because `Documents/` may be ignored.
