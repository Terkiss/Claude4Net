## 0. Product Direction

Claude4Net-App has completed the K023-K028 expansion from a Windows-stable CLI into a file-backed, observable, multi-agent runtime. The next phase should consolidate the runtime into an operational agent platform rather than continue adding isolated features.

The product identity is:

> Claude4Net-App is a trusted execution environment where .NET developers can safely, transparently, resumably, and verifiably delegate real development work to AI agents.

The next roadmap is based on the 2026-05-10 insight report and follows four product pillars:

1. State Discipline: explicit session state machines, checkpoints, rewind, resumability
2. Safe Execution: idempotent file operations, diff-first approval, verifier gates, fail-closed policies
3. Provider Architecture: descriptor-first providers, capability-aware routing, observable health
4. Operational Visibility: replayable events, timeline-based diagnostics, auditable results, controller-grade dashboards

The following detailed themes from the insight set must remain visible in planning:

- real token counting instead of heuristic-only estimates
- handoff and evidence artifacts as completion preconditions
- fresh-context evaluator separation with default-fail verification contracts
- CQRS-style event projections for dashboard scalability
- agentic search as the first recall path, with RAG as an explicit secondary tool
- audit-log fields designed for enterprise and regulatory traceability

CLI-first execution remains the primary product rule. Dashboard work is allowed only when it directly improves operations, visibility, or approvals.

## 3. Operating Roles

### Gemini CLI Worker

- Implements assigned work
- Modifies code, tests, and docs
- Runs the official release gate
- Does not commit or push

### Gemini 3.1 Pro First Reviewer

- Reviews worker output
- Checks staged and unstaged diffs
- Re-runs the release gate when needed
- Writes P1/P2/P3 findings
- If work is not ready, writes the correction prompt
- Does not escalate to Codex until blocking findings are cleared
- Does not commit or push

### Codex Final Controller

- Reads the actual repository state before trusting reports
- Makes final approval, commit, and push decisions
- May directly perform small, scoped, evidence-backed documentation or hygiene corrections
- Keeps branch policy and release gates aligned

Problem statement:

The Gemini provider can inspect the same workspace and continue through tool calls, but the Ollama provider can misread `LsTool` output as empty. Final-controller inspection found that `AgentLoop` builds provider tool results with `result.Content?.ToString()`, which can collapse structured results into CLR strings such as `System.Collections.Generic.List...`. `OllamaProvider.AddMessage` also reads `tool_result.content` with `GetString()` only, so non-string structured content is not safely preserved. This is a P1 provider grounding bug, not a model-specific prompt issue. K036 also covers making the local Ollama context window explicit: the current provider limit is 8,192 tokens and the descriptor is 8,000, while the target experimental operating window is approximately 256k tokens. The worker must implement this as a guarded/configurable Ollama setting with tests, not as an unreviewed administrator patch.

Required fix:

1. Preserve structured tool result payloads when `AgentLoop` passes tool results back to providers.
2. Keep display summaries separate from provider payloads.
3. Update `OllamaProvider.AddMessage` so string content stays string, while object/array content is serialized with `GetRawText()`.
4. Ensure Ollama `/api/chat` request bodies never contain CLR type strings such as `System.Collections.Generic.List` for `LsTool` entries.
5. Do not regress Gemini, Gemini CLI, Claude, or common tool execution behavior.
6. Raise Ollama context handling from the current 8k metadata/runtime limit toward a 256k experimental target.
7. Keep provider metadata, `OllamaProvider.ContextLimit`, and Ollama request `options.num_ctx` consistent.
8. Add a safety note or guard for high context values because 256k can exceed some local model or hardware limits.

Required tests:

1. `AgentLoop_ToolResultPayload_ShouldPreserveStructuredContent`
2. `OllamaProvider_AddMessage_ToolResultObjectContent_ShouldUseRawJson`
3. `OllamaProvider_AddMessage_ToolResultStringContent_ShouldKeepString`
4. `LsTool_ResultSerialization_ShouldExposeEntries`
5. `OllamaProvider_ContextWindow_ShouldExposeConfiguredHighContext`
6. `ProviderRegistry_OllamaDescriptor_ShouldMatchOllamaContextLimit`
7. `OllamaProvider_StreamQuery_ShouldSendNumCtxOption`

Required verification:

- `git status --short --branch`
- `git diff --cached --name-status`
